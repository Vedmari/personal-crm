# Личная CRM

Приложение для ведения контактов людей, которых знаешь лично: кто это, откуда знакомы, телефон и почта, о чём договорились, заметки после разговоров.

Идея и ограничения — в [specs/01-продуктовая-идея.md](specs/01-продуктовая-идея.md), требования фич — в [openspec/specs/](openspec/specs/).

## Что умеет

- Список всех контактов по алфавиту
- Поиск по имени и по полю «Кто это»: слова в любом порядке, «е» и «ё» считаются одной буквой
- Добавление контакта — он сразу появляется в списке и подсвечивается
- Карточка контакта: данные, поле «О чём договорились», лента заметок с датами
- Правка и удаление контакта, удаление заметок. Перед удалением приложение спрашивает подтверждение, а потом ещё 10 секунд можно нажать «Вернуть»
- «Как часто общаться» в карточке: раз в неделю, месяц, квартал или год. Сохраняется сразу после выбора. Под ним срок: «Связаться не позже 24 ноября» или «Пора связаться: срок был 12 октября». Срок считается от последней заметки, а если заметок нет — от момента, когда выбрали частоту
- Блок «Пора связаться» на главной, над списком: контакты, у которых срок прошёл, самые просроченные сверху. Сначала видно пять, остальные — по «Показать все». Кнопка «Связались» в строке добавляет в карточку заметку «Связались», и человек уходит из блока; 10 секунд её можно отменить
- Все даты и время — по московскому времени, где бы ни работал сервер
- Группы контактов: «Семья», «Друзья», «Теннис» — любые, какие придумаешь сам. Контакт может быть в нескольких группах. В карточке строка «Группы»: кнопка «В группу» открывает список с галочками, они сохраняются сразу, а новую группу можно вписать там же
- Под поиском на главной — кнопки «Все» и группы с числом людей: нажал группу, и в списке только она. Работает вместе с поиском, выбранная группа видна в адресе страницы. Пока группа выбрана, блока «Пора связаться» нет
- Страница «Группы» (ссылка «Группы →» на главной): создать, переименовать и удалить группу. Удаление спрашивает подтверждение; контакты из удалённой группы остаются в списке

## Как запустить

Нужны: [Podman Desktop](https://podman-desktop.io/), [Node.js](https://nodejs.org/) 24 и [pnpm](https://pnpm.io/). Вместе с Podman Desktop должны стоять сам Podman и Compose — без них команда `podman compose` не работает.

Docker Desktop не используем: на рабочем ноутбуке он запрещён.

Все команды выполняются в папке проекта.

### Первый запуск

1. Создать файл `.env` по образцу `.env.example` и заполнить значения. Если `.env` уже есть — шаг пропустить.
2. Запустить Podman Desktop и подождать около минуты, пока он запустит Podman.
3. Поднять базу данных:

   ```bash
   podman compose up -d
   ```

4. Установить зависимости:

   ```bash
   pnpm install
   ```

5. Создать таблицы в базе:

   ```bash
   pnpm db:migrate
   ```

6. Наполнить базу тестовыми данными — 1000 контактов с заметками (по желанию):

   ```bash
   pnpm db:seed
   ```

   Команда работает только на пустой базе и ничего не удаляет. Если контакты уже есть, она остановится.

7. Собрать и запустить приложение:

   ```bash
   pnpm build
   pnpm start
   ```

8. Открыть в браузере <http://localhost:3000>.

### Каждый следующий раз

1. Запустить Podman Desktop и подождать около минуты, пока он запустит Podman.
2. Поднять базу: `podman compose up -d`. Сама она после перезагрузки не стартует.
3. Выполнить `pnpm start`.
4. Открыть <http://localhost:3000>.

Остановить приложение — `Ctrl + C` в терминале, где оно запущено.

Если вместо списка появилось «Не получилось загрузить данные» — не запущена база: запустите Podman Desktop, выполните `podman compose up -d` и нажмите «Попробовать снова».

## Доступ

Приложение работает в двух местах, у каждого своя база:

- **На этом компьютере** — <http://localhost:3000>. Приложение и база доступны только отсюда.
- **На сервере** — <https://app.lichnaya-crm.ru>. Открыто всем, у кого есть адрес. Входа по паролю нет: любой, кто откроет адрес, увидит и сможет менять контакты. Поэтому на сервере только тестовые данные — настоящие контакты туда не вносите.

## Выкатка на сервер

### Как выкатить новую версию

1. Закоммитить изменения в свою ветку, отправить её на GitHub и открыть PR в `main` с автовлитием (`gh pr merge --auto --squash`). Напрямую в `main` отправить нельзя: ветка защищена.
2. На PR запускается CI — около 3 минут. Зелёный CI — PR вливается в `main` сам. Красный — не вливается, даже вручную: надо починить причину и отправить исправление в ту же ветку.
3. После влития выкатка идёт сама, ещё 3–5 минут. Ход проверок и выкатки виден на GitHub во вкладке **Actions** (или командой `gh run watch`): зелёная галочка — новая версия на сервере, красный крестик — выкатка упала.
4. Проверить: <https://app.lichnaya-crm.ru/health> показывает `{"status":"ok"}`, на <https://app.lichnaya-crm.ru> видны изменения.

Больше ничего делать не нужно: на сервер заходить не надо.

### Что проверяет CI

На каждый PR в `main` (`.github/workflows/ci.yml`) три проверки идут параллельно, и все три должны быть зелёными:

- **Checks** — линтер (`pnpm lint`), формат (`pnpm format:check`), типы (`pnpm typecheck`), автотесты Vitest (`pnpm test`);
- **E2E** — сквозные тесты в Chrome (`pnpm test:e2e`). Если тест упал, скриншот и запись прогона лежат в артефакте `e2e-results` на странице прогона;
- **Image** — сборка образа приложения: образ только собирается, на сервер его кладёт выкатка после влития.

База для тестов в CI — отдельная временная PostgreSQL, она исчезает вместе с прогоном.

Защита `main` в GitHub (Settings → Branches): изменения только через PR, все три проверки зелёные, правило действует и для администратора.

### Что происходит после push

1. GitHub Actions собирает образ приложения, помечает его номером коммита и кладёт в хранилище образов GitHub (GHCR).
2. Подключается к серверу по ключу деплоя, копирует папку `deploy/` на сервер и запускает `deploy/deploy.sh`.
3. Скрипт на сервере:
   1. скачивает новый образ;
   2. запускает базу, если она не работает;
   3. применяет миграции отдельным разовым контейнером из нового образа;
   4. запускает приложение из нового образа;
   5. проверяет, что `/health` отвечает 200;
   6. удаляет старые образы: остаются только текущий и предыдущий.

Пока идёт выкатка, следующий push ждёт своей очереди.

### Если выкатка упала

- **Упали миграции** — новая версия не запускалась, на сервере работает прежняя.
- **Упала проверка `/health`** — новая версия запущена, но не отвечает. Сама она не откатывается. Вернуть предыдущую версию:

  ```bash
  ssh crm bash /opt/crm/prod/deploy/rollback.sh
  ```

  Откат возвращает только приложение: миграции остаются применёнными.
- Посмотреть, что пишет приложение: `ssh crm docker logs --tail 100 prod-app-1`.

### Что где лежит

- Вход на сервер — `ssh crm`. Всё приложение — в папке `/opt/crm/prod`:
  - `.env` — пароль базы. Права 600: читает только владелец. В git не попадает
  - `release.env` — какая версия работает сейчас и какая была до неё. Пишет скрипт выкатки
  - `deploy/` — скрипты выкатки; каждая выкатка кладёт их заново из репозитория
- Docker Compose, проект `prod`: контейнеры `prod-app-1` (приложение) и `prod-postgres-1` (база). Данные базы — в томе `prod_postgres_data`.
- nginx отдаёт `app.lichnaya-crm.ru` из приложения на `127.0.0.1:3000`. Снаружи до приложения и базы напрямую не достучаться.
- Настройки репозитория в GitHub (Settings → Secrets and variables → Actions): секрет `DEPLOY_SSH_KEY` — ключ деплоя; переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` — адрес сервера, пользователь и отпечаток сервера.

### Тестовые данные на сервере

Пустую базу на сервере можно наполнить 1000 тестовых контактов:

```bash
ssh crm bash /opt/crm/prod/deploy/seed.sh
```

Как и локально, команда работает только на пустой базе и ничего не удаляет. Примерно у каждого десятого тестового контакта задана частота общения, поэтому блок «Пора связаться» на новой базе сразу не пустой. В базе, наполненной раньше, частоты нет — задайте её в нескольких карточках руками.

## Для разработки

| Команда | Что делает |
| --- | --- |
| `pnpm dev` | Запуск в режиме разработки: изменения в коде видны сразу. Работает заметно медленнее: список из 1000 контактов открывается около 10 секунд |
| `pnpm build` | Сборка быстрой версии. Нужна после каждого изменения кода, перед `pnpm start` |
| `pnpm start` | Запуск собранной версии |
| `pnpm lint` | Проверка кода линтером |
| `pnpm format` | Привести код к единому виду (Prettier). Запускать перед коммитом: CI проверяет формат |
| `pnpm format:check` | Только проверить формат, ничего не меняя |
| `pnpm test` | Автотесты (Vitest). Нужен запущенный Podman: тесты сами создают тестовую базу, см. ниже |
| `pnpm test:e2e` | Сквозные тесты в браузере (Playwright): собирают приложение и проходят главный сценарий и основные пути «Пора связаться» в Chrome. Нужны запущенный Podman и установленный Google Chrome, см. ниже |
| `pnpm typecheck` | Проверка типов |
| `pnpm db:generate` | Создать миграцию после изменения схемы в `src/db/schema.ts` |
| `pnpm db:migrate` | Применить миграции к базе |
| `pnpm db:seed` | Наполнить пустую базу тестовыми контактами и группами |

### Автотесты

Тесты — [Vitest](https://vitest.dev). Для каждого сценария требований есть свой тест, и пишется он раньше кода: сначала красный, потом код, потом зелёный.

```bash
podman machine start
podman compose up -d
pnpm test
```

Первые две команды нужны, если Podman не запущен. Если он не запущен, `pnpm test` так и скажет.

Запросы к базе тесты проверяют на настоящей PostgreSQL, а не на заглушках. Для этого у них своя база: то же имя, что у рабочей, и окончание `_test` (например, `personal_crm_test`), в том же контейнере. При первом запуске тесты сами её создают и применяют миграции, `.env` менять не нужно. Перед каждым тестом таблицы тестовой базы очищаются; к рабочей базе тесты не подключаются, а если имя базы не кончается на `_test`, останавливаются.

Тесты не проверяют, как выглядят экраны: это ручная проверка и сквозные тесты в браузере.

### Сквозные тесты (e2e)

Сквозные тесты — [Playwright](https://playwright.dev): открывают приложение в браузере и проходят сценарий, как человек, без заглушек — с настоящим сервером и настоящей базой. Сейчас защищены:

- главный сценарий из `specs/01-продуктовая-идея.md`: открыла список → добавила контакт → нашла по имени → дописала заметку → заметка на месте после обновления страницы и в другом браузере;
- основные пути «Пора связаться»: «Связались» в блоке, выбор частоты в карточке, «Отменить» после «Связались», «Показать все» и «Свернуть». Как считается срок, проверяют автотесты на базе (`src/db/keep-in-touch.db.test.ts`).

```bash
podman machine start
podman compose up -d
pnpm test:e2e
```

Команда сама собирает приложение (`pnpm build`), запускает его на порту 3200 и после тестов останавливает. Прогон занимает около 30–40 секунд. Если на порту 3200 уже что-то запущено, тесты пойдут туда, а не в свежую сборку: такой процесс перед прогоном лучше остановить.

Браузер — Google Chrome, установленный на компьютере: Playwright не скачивает свой. У тестов своя база: имя рабочей с окончанием `_e2e_test` (например, `personal_crm_e2e_test`), в том же контейнере. Перед прогоном тесты сами создают её и применяют миграции. Перед каждым тестом таблицы очищаются, и в базу кладутся два контакта, с которых начинается сценарий, плюс люди, нужные этому тесту: так тесты не зависят друг от друга и от порядка запуска. Рабочие контакты не трогаются, `.env` менять не нужно.

Если тест упал, в `test-results/` остаются скриншот и запись прогона; открыть запись: `pnpm exec playwright show-trace test-results/<папка теста>/trace.zip`.

### Фичи через OpenSpec

Фичи делаем по [OpenSpec](https://openspec.dev): сначала требования, потом код. Требования пишутся на русском. Для этого нужен CLI OpenSpec, он ставится один раз на компьютер:

```bash
npm install -g @fission-ai/openspec@latest
openspec config set telemetry.enabled false
```

Вторая команда отключает анонимную статистику, которую OpenSpec по умолчанию отправляет своим разработчикам.

Команды в Claude Code:

| Команда | Что делает |
| --- | --- |
| `/opsx:propose <имя> - <суть>` | Описать изменение: что и зачем, требования, технические решения, задачи |
| `/opsx:update <имя>` | Согласовать между собой файлы изменения после правок |
| `/opsx:apply <имя>` | Реализовать изменение по задачам |
| `/opsx:archive <имя>` | Перенести готовые требования в действующие |

После обновления CLI выполнить в папке проекта `openspec update` — он обновит команды OpenSpec для Claude Code.

## Как устроено

- `src/app` — страницы: список контактов (`page.tsx`), карточка (`contacts/[id]/page.tsx`), серверные действия (`actions.ts`)
- `src/components` — части интерфейса; `src/components/ui` — компоненты shadcn/ui. Блок «Пора связаться» — `keep-in-touch-block.tsx` и `keep-in-touch-list.tsx`, выбор частоты в карточке — `keep-in-touch-select.tsx`
- `src/lib/format.ts` — как показываются даты, числа и подписи. Часовой пояс всех дат — `MOSCOW_TIME_ZONE`
- `src/styles/tokens.css` — цвета, шрифты, размеры текста и отступы. Это точная копия файла из лендинга (`personal-crm-landing/src/styles/tokens.css`): меняете один — поменяйте и второй. Шаг отступов — 1 пиксель, поэтому `p-16` — это 16 пикселей
- `src/app/globals.css` — подключает Tailwind и токены, переносит из лендинга фактуры бумаги (линейка, поля, корешок, стикер)
- `public/paper-noise.svg` — зернистость бумаги, тот же файл, что в лендинге
- `src/db` — схема таблиц (`schema.ts`), подключение и запросы к базе. С базой работает только сервер, браузер к ней не обращается. Срок «Пора связаться» для карточки и блока считает один SQL-фрагмент в `queries.ts`. Группы — таблицы `groups` и `contact_groups` (кто в какой группе)
- `src/app/groups/page.tsx` — страница «Группы»; ряд кнопок-фильтров на главной — `group-filter.tsx`, выбор групп в карточке — `contact-groups-picker.tsx`. Все ссылки на список (поиск и группа в адресе) собирает `listHref` в `src/lib/list-filter.ts`
- `*.test.ts` рядом с кодом — тесты чистых функций, `*.db.test.ts` — тесты запросов и серверных действий на тестовой базе; общее для них — в `test/`, настройки — `vitest.config.mts`
- `e2e` — сквозные тесты в браузере: главный сценарий — `main-scenario.spec.ts`, «Пора связаться» — `keep-in-touch.spec.ts`, подготовка базы — `global-setup.ts` и `resetDatabase` в `database.ts`; настройки — `playwright.config.ts`
- `drizzle` — миграции базы
- `src/app/health/route.ts` — адрес `/health` для проверки после выкатки: 200, если приложение работает и видит базу
- `scripts/seed.mts` — генератор тестовых данных
- `scripts/migrate.mts` — применяет миграции на сервере (локально — `pnpm db:migrate`)
- `docker-compose.yml` — PostgreSQL в контейнере для этого компьютера. Имя файла стандартное для Compose, запускается он через Podman
- `Dockerfile` — как собирается образ приложения для сервера
- `deploy/` — выкатка на сервере: `compose.yaml` (приложение и база), `deploy.sh` (выкатка), `rollback.sh` (ручной откат), `seed.sh` (тестовые данные)
- `.github/workflows/deploy.yml` — автовыкатка после push в `main`
- `openspec` — требования фич: `specs` — действующие, `changes` — изменения в работе, `changes/archive` — завершённые изменения, `config.yaml` — настройки OpenSpec
- `.claude/skills/openspec-*` и `.claude/commands/opsx` — команды OpenSpec для Claude Code. Их создаёт `openspec init` и обновляет `openspec update`, руками не правим
- `backups` — копии базы данных, в git не попадают

Оформление — в стиле лендинга: листы записной книжки на зелёной обложке. Шрифты Alegreya, Alegreya Sans и Caveat лежат внутри приложения (пакеты Fontsource, те же, что в лендинге), с Google ничего не грузится.

Стек: Next.js (App Router), TypeScript, React, Tailwind CSS, shadcn/ui, PostgreSQL, Drizzle, pnpm.
