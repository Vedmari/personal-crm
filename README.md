# Личная CRM

Приложение для ведения контактов людей, которых знаешь лично: кто это, откуда знакомы, телефон и почта, о чём договорились, заметки после разговоров.

Идея и ограничения — в [specs/01-продуктовая-идея.md](specs/01-продуктовая-идея.md), требования фич — в [openspec/specs/](openspec/specs/).

## Что умеет

- Вход по ссылке из письма, без паролей: ввели почту — пришла ссылка «Войти». Первый вход под новой почтой и есть регистрация. Каждый видит и меняет только свои контакты, заметки и группы. Вход держится 30 дней с последнего захода, «Выйти» — над листом, на всех страницах
- Список всех контактов по алфавиту, по 100 человек: следующие — по кнопке «Показать ещё». Сколько показано, видно в адресе страницы, поэтому «Назад» из карточки возвращает на то же место
- Поиск по имени и по полю «Кто это»: слова в любом порядке, «е» и «ё» считаются одной буквой
- Добавление контакта — он сразу появляется в списке и подсвечивается
- Карточка контакта: данные, поле «О чём договорились», лента заметок с датами
- Правка и удаление контакта, удаление заметок. Перед удалением приложение спрашивает подтверждение, а потом ещё 10 секунд можно нажать «Вернуть»
- «Как часто общаться» в карточке: раз в неделю, месяц, квартал или год. Сохраняется сразу после выбора. Под ним срок: «Связаться не позже 24 ноября» или «Пора связаться: срок был 12 октября». Срок считается от последней заметки, а если заметок нет — от момента, когда выбрали частоту
- Блок «Пора связаться» на главной, над списком: контакты, у которых срок прошёл, самые просроченные сверху. Сначала видно пять, остальные — по «Показать все». Кнопка «Связались» в строке добавляет в карточку заметку «Связались», и человек уходит из блока; 10 секунд её можно отменить
- Все даты и время — по московскому времени, где бы ни работал сервер
- Группы контактов: «Семья», «Друзья», «Теннис» — любые, какие придумаешь сам. Контакт может быть в нескольких группах. В карточке строка «Группы»: кнопка «В группу» открывает список с галочками, они сохраняются сразу, а новую группу можно вписать там же
- Под поиском на главной — кнопки «Все» и группы с числом людей: нажал группу, и в списке только она. Работает вместе с поиском, выбранная группа видна в адресе страницы. Пока группа выбрана, блока «Пора связаться» нет
- Страница «Группы» (ссылка «Группы →» на главной): создать, переименовать и удалить группу. Удаление спрашивает подтверждение; контакты из удалённой группы остаются в списке

## Как запустить

Нужны: [Podman Desktop](https://podman-desktop.io/), [Node.js](https://nodejs.org/) 24 и [pnpm](https://pnpm.io/). Вместе с Podman Desktop должны стоять сам Podman и Compose — без них команда `podman compose` не работает.

Docker Desktop не используем: на рабочем ноутбуке он запрещён.

Все команды выполняются в папке проекта.

### Первый запуск

1. Создать файл `.env` по образцу `.env.example` и заполнить значения. Если `.env` уже есть — сверить его с `.env.example` и дописать недостающие строки. Для этого компьютера:

   | Строка | Значение |
   | --- | --- |
   | `BETTER_AUTH_SECRET` | случайная строка: результат команды `openssl rand -base64 32` |
   | `BETTER_AUTH_URL` | `http://localhost:3000` |
   | `SMTP_URL` | `smtp://localhost:1025` |
   | `OWNER_EMAIL` | ваша почта: контакты, которые уже есть в базе, и тестовые данные будут вашими |
   | `MAILPIT_URL` | можно оставить пустой |

2. Запустить Podman Desktop и подождать около минуты, пока он запустит Podman.
3. Поднять базу данных и почтовую заглушку Mailpit:

   ```bash
   podman compose up -d
   ```

   Mailpit ловит все письма, которые отправляет приложение на этом компьютере: на настоящую почту они не уходят. Письма видны на странице <http://localhost:8025>.

4. Установить зависимости:

   ```bash
   pnpm install
   ```

5. Создать таблицы в базе:

   ```bash
   pnpm db:migrate
   ```

   Та же команда обновляет базу после изменений в коде. Если в базе уже есть контакты, а `OWNER_EMAIL` в `.env` не задана, обновление до входа по почте остановится с ошибкой и ничего не изменит. В конце команда пишет, сколько контактов, заметок и групп было до обновления и сколько стало.

6. Наполнить базу тестовыми данными — 1000 контактов с заметками (по желанию):

   ```bash
   pnpm db:seed
   ```

   Команда работает только на пустой базе и ничего не удаляет. Если контакты уже есть, она остановится.

7. Собрать и запустить приложение:

   ```bash
   pnpm build
   pnpm start
   ```

8. Открыть в браузере <http://localhost:3000> и войти: ввести почту, нажать «Получить ссылку», открыть письмо на <http://localhost:8025> и нажать в нём «Войти». Под почтой из `OWNER_EMAIL` видны все прежние контакты, под любой другой — пустой список.

### Каждый следующий раз

1. Запустить Podman Desktop и подождать около минуты, пока он запустит Podman.
2. Поднять базу и Mailpit: `podman compose up -d`. Сами они после перезагрузки не стартуют.
3. Выполнить `pnpm start`.
4. Открыть <http://localhost:3000>. Вход держится 30 дней с последнего захода, письмо каждый раз не нужно.

Остановить приложение — `Ctrl + C` в терминале, где оно запущено.

Если вместо списка появилось «Не получилось загрузить данные» — не запущена база: запустите Podman Desktop, выполните `podman compose up -d` и нажмите «Попробовать снова».

## Доступ

Приложение работает в трёх местах. У каждого своя база, свои ключи и свой вход:

- **На этом компьютере** — <http://localhost:3000>. Приложение и база доступны только отсюда. Письма со ссылкой для входа никуда не уходят: их ловит Mailpit, они видны на <http://localhost:8025>.
- **Тест-стенд** — <https://test-app.lichnaya-crm.ru>. Закрыт паролем, на нём копия данных прода. Сюда новая версия попадает сразу после влития в `main`, чтобы проверить её на настоящих данных (см. «Тест-стенд»).
- **Прод** — <https://app.lichnaya-crm.ru>. Письма со ссылкой приходят на настоящую почту, их отправляет сервис Resend.

Ссылка во входном письме ведёт туда, где вход запросили: со стенда — на стенд, с прода — на прод. Вход на стенде и на проде не связан: кука входа остаётся на своём адресе, и вход на одном не трогает вход на другом.

Без входа приложение не открывается: любая страница ведёт на страницу входа. Войти можно только по ссылке из письма. Ссылка работает один раз и 15 минут, новая ссылка отменяет прежние, на одну почту уходит не больше трёх писем за 10 минут.

Каждый пользователь видит и меняет только свои контакты, заметки и группы: и в интерфейсе, и при прямом запросе к серверу. Поэтому на сервере можно хранить настоящие контакты и пускать друзей: чужого никто не увидит.

Контакты, заметки и группы, которые были в базе до появления входа, и тестовые данные принадлежат пользователю с почтой из `OWNER_EMAIL`.

Вход держится 30 дней с последнего захода на этом устройстве. Можно входить с нескольких устройств сразу. «Выйти» завершает вход только на этом устройстве.

## Выкатка на сервер

### Как выкатить новую версию

1. Влейте PR в `main` после зелёного CI. Во вкладке **Actions → Deploy staging** дождитесь зелёной выкатки и проверьте изменения на [тест-стенде](https://test-app.lichnaya-crm.ru). После merge прод продолжает работать на прежней версии.
2. Для выкатки откройте [Actions → Deploy prod](https://github.com/Vedmari/personal-crm/actions/workflows/deploy-prod.yml) под учётной записью владельца. Нажмите **Run workflow** и выберите ветку `main`.
3. Оставьте **Commit SHA** пустым, чтобы выкатить последнюю успешную версию стенда на момент запуска. Если проверяли конкретную версию, вставьте её полный SHA (40 знаков). GitHub проверит её по истории успешных выкаток на стенд. Галочку **Roll back** оставьте снятой и нажмите **Run workflow**.
4. В **Summary** запуска сверьте полный SHA с ожидаемым. Откройте [проверку прода](https://app.lichnaya-crm.ru/health) — ответ должен быть `{"status":"ok"}`. Войдите в [CRM](https://app.lichnaya-crm.ru) и проверьте изменение на своём контакте.

### Как откатить прод

1. Откройте **Actions → Deploy prod → Run workflow**, выберите `main`, поставьте **Roll back** и запустите workflow. Поле SHA при откате игнорируется.
2. Сервер возьмёт предыдущий образ прода с диска. После зелёной проверки сверьте SHA в **Summary**, откройте `/health` и проверьте вход в CRM. При красной проверке откройте шаг с ошибкой. Повторный откат переключит приложение обратно на версию, с которой вы только что ушли.
3. Откат переключает приложение. Миграции и данные сохраняются. Если нужно вернуть и базу, выберите подходящий бэкап и следуйте разделу «Бэкапы и восстановление».

### Настройки на сервере

Секреты и настройки прода лежат в `/opt/crm/prod/.env`, тест-стенда — в `/opt/crm/staging/.env` (у обоих права 600, в git не попадают). Строки одни и те же, значения свои: у стенда свой пароль базы, свой секрет входа, свой адрес и свой ключ Resend. Ключи прода в окружение стенда не передаются, но на стенде есть копия его данных, поэтому доступ к нему тоже нужно защищать. Если какой-то строки нет, выкатка остановится на первом шаге, до бэкапа и миграций, и в логе будет написано, какой строки не хватает.

| Строка | Что это и откуда взять |
| --- | --- |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | база данных |
| `BETTER_AUTH_SECRET` | секрет, которым подписан вход. Случайная строка: результат команды `openssl rand -base64 32`. Если его поменять, все выйдут и войдут заново |
| `BETTER_AUTH_URL` | адрес окружения, сюда ведут ссылки в письмах: `https://app.lichnaya-crm.ru` на проде, `https://test-app.lichnaya-crm.ru` на стенде |
| `SMTP_URL` | куда отправлять письма: `smtps://resend:<API-ключ>@smtp.resend.com:2465`. Порт 2465, а не обычный 465: провайдер сервера закрывает исходящие 465 и 587, а у Resend это запасной порт с тем же шифрованием. Ключ — в [Resend](https://resend.com), раздел API Keys, с правом только на отправку с домена `mail.crm.lichnaya-crm.ru`; у прода и у стенда (ключ `staging`) ключи разные. Домен подтверждается в Resend записями DNS |
| `OWNER_EMAIL` | ваша почта: ей достаются контакты, которые были на сервере до появления входа, и тестовые данные `seed.sh`. На стенде — та же почта, что на проде |

Отправитель писем — «Личная CRM» `noreply@mail.crm.lichnaya-crm.ru`, он одинаков везде.

### Тест-стенд

<https://test-app.lichnaya-crm.ru> — второе приложение на том же сервере. Сюда каждая новая версия попадает сразу после влития в `main`, тем же скриптом и тем же образом, что прод.

- **Пароль.** На стенде данные пользователей, поэтому перед приложением браузер спрашивает логин `test` и пароль. Пароль хранится на сервере в `/etc/nginx/test-app.htpasswd` в зашифрованном виде; пока этого файла нет, стенд отвечает ошибкой и не открывается вовсе. Задать или сменить пароль (команда спросит его дважды, на экране он не виден):

  ```bash
  ssh -t crm 'h="$(openssl passwd -6)" && [ -n "$h" ] && printf "test:%s\n" "$h" | sudo tee /etc/nginx/test-app.htpasswd >/dev/null && sudo chown root:www-data /etc/nginx/test-app.htpasswd && sudo chmod 640 /etc/nginx/test-app.htpasswd && echo "Пароль стенда задан"'
  ```

  Дальше вход в приложение — как на проде, по ссылке из письма. Письма настоящие: стенд отправляет их через Resend своим ключом.
- **Данные.** База стенда — копия базы прода из последнего бэкапа. Первая выкатка на пустую базу загружает её сама, следующие выкатки данные стенда не трогают. В копии нет входов прода: на стенде каждый входит заново.
- **Испортилась база стенда** — сделать её заново из свежего бэкапа прода. Скрипт покажет, какой файл возьмёт, и попросит напечатать `yes`. Всё, что меняли на стенде, пропадёт. Прод при этом не меняется:

  ```bash
  ssh -t crm bash /opt/crm/staging/deploy/reset-staging-db.sh
  ```

- **Свой сертификат** `test-app.lichnaya-crm.ru`, certbot продлевает его сам, как и сертификат прода.
- **Бэкапов у стенда нет**: его данные — копия прода, их не жалко.
- **Память.** У каждого контейнера на сервере есть предел памяти: приложение 512 МБ, база 256 МБ. Так стенд не может занять память прода. Контейнер, который упёрся в предел, перезапускается сам, остальные работают дальше.

### Что проверяет CI

На каждый PR в `main` (`.github/workflows/ci.yml`) три проверки идут параллельно, и все три должны быть зелёными:

- **Checks** — линтер (`pnpm lint`), формат (`pnpm format:check`), типы (`pnpm typecheck`), автотесты Vitest (`pnpm test`);
- **E2E** — сквозные тесты в Chrome (`pnpm test:e2e`). Если тест упал, скриншот и запись прогона лежат в артефакте `e2e-results` на странице прогона;
- **Image** — сборка образа приложения: образ только собирается, на сервер его кладёт выкатка после влития.

База для тестов в CI — отдельная временная PostgreSQL, она исчезает вместе с прогоном.

Защита `main` в GitHub (Settings → Branches): изменения только через PR, все три проверки зелёные, правило действует и для администратора.

### Как устроена выкатка

После push в `main` GitHub Actions публикует в GHCR образ с полным SHA коммита и выкатывает его на стенд. Успешная проверка `/health` попадает в историю окружения `staging` в GitHub. При ручной выкатке прод скачивает тот же образ по SHA.

Для каждого окружения workflow копирует папку `deploy/` на сервер. Скрипт выкатки ждёт освобождения окружения, скачивает образ и запускает PostgreSQL. На проде он снимает бэкап до миграций. На стенде при первом запуске с пустой базой загружает последний бэкап прода. Затем разовый контейнер применяет миграции, приложение запускается на новом образе, скрипт проверяет `/health`.

После успешной выкатки на прод сервер очищает образы CRM старше 14 дней. Он сохраняет текущую и предыдущую версии прода и текущую версию стенда независимо от возраста. В GHCR остаются десять последних сборок с SHA-тегами. Для выкатки по вручную введённому SHA образ должен ещё быть в GHCR. Если шаг очистки упал после успешной проверки приложения, версия уже работает на проде. Для удаления старых версий пакет GHCR должен давать этому репозиторию право **Admin** в **Manage Actions access**.

Две выкатки на одно окружение одновременно не идут. Текущий запуск не прерывается; GitHub хранит один ожидающий запуск, и более новый push может заменить его. Поэтому промежуточные коммиты могут не попасть на сервер отдельной выкаткой.

### Если выкатка упала

- **Упали миграции** — новая версия не запускалась, на сервере работает прежняя.
- **Упала проверка `/health`** — новая версия запущена, но не отвечает. Сама она не откатывается. Для прода используйте кнопку из раздела «Как откатить прод». Для стенда, если предыдущий образ ещё на сервере, выполните команду:

  ```bash
  ssh crm bash /opt/crm/staging/deploy/rollback.sh staging
  ```

  Откат возвращает только приложение: миграции остаются применёнными. Если новая версия испортила данные, базу можно вернуть из бэкапа, снятого перед выкаткой (см. «Бэкапы и восстановление»).
- **Упал бэкап** (прод) **или загрузка копии прода** (стенд) — миграции не применялись, новая версия не запускалась, работает прежняя. Причина — в логе выкатки на GitHub.
- **Откат выкатки, с которой появился вход, — только вместе: приложение и база.** Её миграция дала каждому контакту и группе владельца, и прежняя версия на такой базе не сможет добавить контакт. Поэтому сначала откатите приложение через **Deploy prod**, затем запустите `restore.sh` с бэкапом, снятым перед этой выкаткой. Имя файла — в логе выкатки, в шаге «Backing up the database»:

  ```bash
  ssh -t crm bash /opt/crm/prod/deploy/restore.sh <имя бэкапа перед выкаткой>
  ```

  Всё, что добавили на сервере после этой выкатки, при таком откате пропадёт: перед заменой базы `restore.sh` сохранит её копию.
### Как читать логи

Последние 100 строк приложения на проде:

```bash
ssh crm sudo journalctl --no-pager -n 100 CONTAINER_TAG=crm-prod-app
```

На тест-стенде:

```bash
ssh crm sudo journalctl --no-pager -n 100 CONTAINER_TAG=crm-staging-app
```

Чтобы следить за новыми строками, замените `-n 100` на `-f`. Выход — `Ctrl+C`. Для записей за сегодня используйте `--since=today` вместо `-n 100`. Для логов PostgreSQL или миграций замените окончание метки `-app` на `-postgres` или `-migrate`.

С первой выкатки этой настройки журнал сервера (journald) собирает строки по постоянной метке. По одной команде видны записи до и после пересоздания контейнера, включая выкатки и откаты. Старые строки Docker, записанные до перехода, в журнал автоматически не переносятся. Размер журнала ограничивает система: когда место заканчивается, она удаляет самые старые записи.

### Что где лежит

- Вход на сервер — `ssh crm`. Прод — в папке `/opt/crm/prod`, тест-стенд — в `/opt/crm/staging`. В каждой:
  - `.env` — пароль базы, секрет входа, ключ Resend и почта владельца (см. «Настройки на сервере»). Права 600: читает только владелец. В git не попадает
  - `release.env` — какая версия работает сейчас и какая была до неё. Пишет скрипт выкатки
  - `deploy/` — скрипты выкатки; каждая выкатка на это окружение кладёт их заново из репозитория
  - `deploy.lock` — замок: пока идёт выкатка, откат или восстановление, следующий скрипт на этом окружении ждёт
- `/opt/crm/prod/backups/` — бэкапы базы прода. В них персональные данные: папку и файлы читает только владелец. Отсюда же стенд берёт копию прода.
- Docker Compose, проекты `prod` и `staging`. Контейнеры прода — `prod-app-1` (приложение) и `prod-postgres-1` (база), данные базы — в томе `prod_postgres_data`. У стенда так же: `staging-app-1`, `staging-postgres-1`, том `staging_postgres_data`.
- nginx отдаёт `app.lichnaya-crm.ru` из приложения прода на `127.0.0.1:3000`, а `test-app.lichnaya-crm.ru` — из приложения стенда на `127.0.0.1:3001`, только после пароля. Снаружи до приложений и баз напрямую не достучаться.
- Настройки репозитория в GitHub (Settings → Secrets and variables → Actions): секрет `DEPLOY_SSH_KEY` — ключ деплоя; переменные `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_KNOWN_HOSTS` — адрес сервера, пользователь и отпечаток сервера.

### Бэкапы и восстановление

**Бэкап** — копия всей базы в одном файле. Прод снимает бэкап перед миграциями и ежедневно в **03:00 по Москве**. При первой ручной выкатке новой конфигурации сервер включает таймер systemd. Посмотреть ближайший запуск можно командой `ssh crm systemctl list-timers --all crm-db-backup.timer`. После простоя сервера таймер догонит пропущенный запуск.

- Файлы лежат на сервере в `/opt/crm/prod/backups`. Посмотреть список:

  ```bash
  ssh crm ls -lh /opt/crm/prod/backups
  ```

- Имя файла: `2026-11-06_153012_d7ee8bf.dump`, то есть дата, время по UTC (по Москве на 3 часа больше) и версия приложения, которая работала **до** выкатки. Версия — первые 7 знаков номера коммита, как их показывает GitHub. Значит, файл подходит к этой версии приложения.
- Файлы с `_before-restore` в конце — копии, которые снимает восстановление перед тем, как заменить базу.
- В бэкапах персональные данные. Не копируйте их туда, где их могут увидеть другие.
- Ежедневные копии заканчиваются на `_daily.dump`. После 03:00 проверьте, что в списке появился сегодняшний файл (дата и время в имени по UTC). Для проверки последнего запуска выполните `ssh crm systemctl status crm-db-backup.service`.
- После создания и проверки нового файла сервер оставляет семь последних ежедневных копий и отдельно семь копий перед выкаткой. Файлы `_before-restore.dump` хранятся отдельно от этой ротации.

**Восстановление** заменяет всю базу прода содержимым бэкапа. Всё, что изменилось в базе после этого бэкапа, пропадёт: перед заменой скрипт сохраняет копию текущей базы, и из неё можно вернуться обратно. Запускаете только вы, сам сервер этого никогда не делает. Если в этот момент идёт выкатка на прод, скрипт дождётся её конца. Базу стенда так не восстанавливают: её делает заново `reset-staging-db.sh` (см. «Тест-стенд»).

1. Выберите файл. Если запустить скрипт без файла, он покажет список бэкапов и ничего не изменит:

   ```bash
   ssh -t crm bash /opt/crm/prod/deploy/restore.sh
   ```

2. Сравните версию в имени файла с версией приложения на сервере (`ssh crm cat /opt/crm/prod/release.env`, строка `IMAGE_TAG`). Восстановление версию приложения не меняет и миграции не запускает. Если версии разные, приложение может не заработать на старой базе. Обычный порядок после неудачной выкатки такой: сначала откатить приложение (см. «Как откатить прод»), затем восстановить бэкап с версией, на которую откатились.
3. Запустите восстановление с этим файлом. Достаточно имени, путь не нужен:

   ```bash
   ssh -t crm bash /opt/crm/prod/deploy/restore.sh 2026-11-06_153012_d7ee8bf.dump
   ```

   Скрипт проверит, что файл целый, и покажет, какой файл какую базу заменит. Если версии не совпадают, он предупредит. Затем он попросит напечатать `yes`. Любой другой ответ ничего не меняет.
4. После `yes` скрипт сам:
   1. сохраняет копию текущей базы (`…_before-restore.dump`);
   2. останавливает приложение;
   3. удаляет базу, создаёт её заново и загружает в неё бэкап;
   4. запускает приложение той же версии и проверяет `/health`.
5. Проверьте: <https://app.lichnaya-crm.ru/health> показывает `{"status":"ok"}`, на <https://app.lichnaya-crm.ru> видны контакты из бэкапа.

Если загрузка бэкапа упала, приложение остаётся остановленным, а скрипт печатает готовую команду, которая вернёт базу из сохранённой копии. Если упала только проверка `/health`, база уже восстановлена. Посмотрите логи приложения: `ssh crm sudo journalctl --no-pager -n 100 CONTAINER_TAG=crm-prod-app`.

### Тестовые данные на сервере

Пустую базу на сервере можно наполнить 1000 тестовых контактов. Они достаются пользователю с почтой из `OWNER_EMAIL`:

```bash
ssh crm bash /opt/crm/prod/deploy/seed.sh
```

Как и локально, команда работает только на пустой базе и ничего не удаляет. Примерно у каждого десятого тестового контакта задана частота общения, поэтому блок «Пора связаться» на новой базе сразу не пустой. В базе, наполненной раньше, частоты нет — задайте её в нескольких карточках руками.

### Автотесты

Тесты — [Vitest](https://vitest.dev). Для каждого сценария требований есть свой тест, и пишется он раньше кода: сначала красный, потом код, потом зелёный.

```bash
podman machine start
podman compose up -d
pnpm test
```

Первые две команды нужны, если Podman не запущен. Если он не запущен, `pnpm test` так и скажет.

Запросы к базе тесты проверяют на настоящей PostgreSQL, а не на заглушках. Для этого у них своя база: то же имя, что у рабочей, и окончание `_test` (например, `personal_crm_test`), в том же контейнере. При первом запуске тесты сами её создают и применяют миграции, `.env` менять не нужно. Перед каждым тестом таблицы тестовой базы очищаются; к рабочей базе тесты не подключаются, а если имя базы не кончается на `_test`, останавливаются.

Перед каждым тестом в базе есть два пользователя, A и B, и тест работает от имени A. Тесты «чужих данных» переключаются на B и проверяют, что каждый запрос и каждое действие не видят и не меняют записи A. Миграцию, которая дала старым данным владельца, проверяет отдельный тест на своей временной базе `<рабочая>_migration_test`: он создаёт её сам и сам удаляет.

Тест «Письмо не ушло» отправляет письмо на закрытый порт: так сбой почты настоящий, а не подстроенный.

Тесты не проверяют, как выглядят экраны: это ручная проверка и сквозные тесты в браузере.

### Сквозные тесты (e2e)

Сквозные тесты — [Playwright](https://playwright.dev): открывают приложение в браузере и проходят сценарий, как человек, без заглушек — с настоящим сервером, настоящей базой и настоящими письмами в Mailpit. Сейчас защищены:

- вход по ссылке из письма (`login.spec.ts`): страница входа, письмо и его содержимое, почта в разном написании, ошибка в адресе, одноразовая ссылка на 15 минут, отмена старой ссылки, лимит писем, 30 дней входа, два устройства, «Выйти». Время, которого тест не может ждать (16 минут, 30 дней), сдвигается в строках базы;
- два пользователя в двух браузерах (`two-users.spec.ts`): каждый входит по своей ссылке и не видит контактов, заметок и групп другого — в обе стороны;
- главный сценарий из `specs/01-продуктовая-идея.md`: открыла список → добавила контакт → нашла по имени → дописала заметку → заметка на месте после обновления страницы и в другом браузере;
- основные пути «Пора связаться»: «Связались» в блоке, выбор частоты в карточке, «Отменить» после «Связались», «Показать все» и «Свернуть». Как считается срок, проверяют автотесты на базе (`src/db/keep-in-touch.db.test.ts`);
- список порциями по 100: «Показать ещё», поиск и группа по всей книге, длина списка после обновления и «Назад», догрузка до добавленного и возвращённого контакта. Какие строки попадают в порцию, проверяют автотесты на базе (`src/db/list-pages.db.test.ts`).

```bash
podman machine start
podman compose up -d
pnpm test:e2e
```

Команда сама собирает приложение (`pnpm build`), запускает его на порту 3200 и после тестов останавливает. Прогон занимает около 30–40 секунд. Если на порту 3200 уже что-то запущено, тесты пойдут туда, а не в свежую сборку: такой процесс перед прогоном лучше остановить.

Нужен запущенный Mailpit (его поднимает `podman compose up -d`): приложение под тестами отправляет письма туда, а тесты берут из них ссылку для входа. Перед тестами Playwright один раз входит под пользователем `e2e-user@example.com` через форму и письмо и запоминает вход в `e2e/.auth/` (в git не попадает); остальные тесты, кроме входа и двух пользователей, начинаются уже внутри. Тесты входа берут каждый раз новые почты, поэтому лимит писем им не мешает.

Браузер — Google Chrome, установленный на компьютере: Playwright не скачивает свой. У тестов своя база: имя рабочей с окончанием `_e2e_test` (например, `personal_crm_e2e_test`), в том же контейнере. Перед прогоном тесты сами создают её и применяют миграции. Перед каждым тестом таблицы очищаются, и в базу кладутся два контакта, с которых начинается сценарий, плюс люди, нужные этому тесту: так тесты не зависят друг от друга и от порядка запуска. Рабочие контакты не трогаются, `.env` менять не нужно.

Если тест упал, в `test-results/` остаются скриншот и запись прогона; открыть запись: `pnpm exec playwright show-trace test-results/<папка теста>/trace.zip`.

### Фичи через OpenSpec

Фичи делаем по [OpenSpec](https://openspec.dev): сначала требования, потом код. Требования пишутся на русском. Для этого нужен CLI OpenSpec, он ставится один раз на компьютер:

```bash
npm install -g @fission-ai/openspec@latest
openspec config set telemetry.enabled false
```

Вторая команда отключает анонимную статистику, которую OpenSpec по умолчанию отправляет своим разработчикам.

Команды в Claude Code:

| Команда | Что делает |
| --- | --- |
| `/opsx:propose <имя> - <суть>` | Описать изменение: что и зачем, требования, технические решения, задачи |
| `/opsx:update <имя>` | Согласовать между собой файлы изменения после правок |
| `/opsx:apply <имя>` | Реализовать изменение по задачам |
| `/opsx:archive <имя>` | Перенести готовые требования в действующие |

После обновления CLI выполнить в папке проекта `openspec update` — он обновит команды OpenSpec для Claude Code.

## Как устроено

- `src/app` — страницы: список контактов (`page.tsx`), карточка (`contacts/[id]/page.tsx`, «Контакт не найден» — `contacts/[id]/not-found.tsx`), вход (`login/page.tsx`, «Ссылка устарела» — `login/expired/page.tsx`), серверные действия (`actions.ts` — данные, каждое действие сначала проверяет вход; `auth-actions.ts` — «Получить ссылку» и «Выйти»)
- Вход: настройки Better Auth и проверка запроса ссылки (почта, лимит писем, отмена старых ссылок) — `src/lib/auth.ts`; лимит и отмена в базе — `src/db/login-links.ts`; кто вошёл — `src/lib/current-user.ts`; проверка входа на каждой странице и продление входа — `src/proxy.ts`; адреса Better Auth — `src/app/api/auth/[...all]/route.ts`; письмо — `src/lib/login-email.ts`, отправка — `src/lib/mail.ts`; почта и «Выйти» над листом — `src/components/account-bar.tsx`
- Только свои данные: каждый запрос в `src/db/queries.ts` получает владельца первым аргументом и ищет только его записи; у контактов и групп столбец `owner_id`, заметка принадлежит владельцу своего контакта
- `src/components` — части интерфейса; `src/components/ui` — компоненты shadcn/ui. Блок «Пора связаться» — `keep-in-touch-block.tsx` и `keep-in-touch-list.tsx`, выбор частоты в карточке — `keep-in-touch-select.tsx`

- `src/styles/tokens.css` — цвета, шрифты, размеры текста и отступы. Это точная копия файла из лендинга (`personal-crm-landing/src/styles/tokens.css`): меняете один — поменяйте и второй. Шаг отступов — 1 пиксель, поэтому `p-16` — это 16 пикселей
- `src/app/globals.css` — подключает Tailwind и токены, переносит из лендинга фактуры бумаги (линейка, поля, корешок, стикер)

- `src/db` — схема таблиц (`schema.ts`), подключение и запросы к базе. С базой работает только сервер, браузер к ней не обращается. Срок «Пора связаться» для карточки и блока считает один SQL-фрагмент в `queries.ts`. Группы — таблицы `groups` и `contact_groups` (кто в какой группе)

Все ссылки на список (поиск, группа и сколько показано — в адресе) собирает `listHref` в `src/lib/list-filter.ts`, кнопка «Показать ещё» — `show-more-link.tsx`

- `drizzle` — миграции базы
- `src/app/health/route.ts` — адрес `/health` для проверки после выкатки: 200, если приложение работает и видит базу
- `scripts/seed.mts` — генератор тестовых данных
- `scripts/migrate.mts` — применяет миграции на сервере и на этом компьютере (`pnpm db:migrate`): передаёт миграциям почту владельца из `OWNER_EMAIL` и пишет в журнал число контактов, заметок и групп до и после
- `docker-compose.yml` — PostgreSQL и почтовая заглушка Mailpit в контейнерах для этого компьютера. Имя файла стандартное для Compose, запускается он через Podman
- `Dockerfile` — как собирается образ приложения для сервера
- `deploy/` — выкатка на сервере, одни и те же файлы для прода и тест-стенда (окружение — первым параметром): `compose.yaml` (приложение и база), `deploy.sh` (выкатка), `rollback.sh` (ручной откат), `restore.sh` (восстановление базы прода из бэкапа), `reset-staging-db.sh` (база стенда заново из бэкапа прода), `seed.sh` (тестовые данные прода), `lib.sh` (общие части скриптов: окружения, замок, бэкап, копия прода для стенда)
- `.github/workflows/deploy.yml` — автовыкатка на стенд после push в `main`. `.github/workflows/deploy-prod.yml` — ручная выкатка и откат прода
- `openspec` — требования фич: `specs` — действующие, `changes` — изменения в работе, `changes/archive` — завершённые изменения, `config.yaml` — настройки OpenSpec
- `.claude/skills/openspec-*` и `.claude/commands/opsx` — команды OpenSpec для Claude Code. Их создаёт `openspec init` и обновляет `openspec update`, руками не правим
- `backups` — копии базы данных на этом компьютере, в git не попадают. Бэкапы сервера лежат на сервере, см. «Бэкапы и восстановление»

Оформление — в стиле лендинга: листы записной книжки на зелёной обложке. Шрифты Alegreya, Alegreya Sans и Caveat лежат внутри приложения (пакеты Fontsource, те же, что в лендинге), с Google ничего не грузится.

Стек: Next.js (App Router), TypeScript, React, Tailwind CSS, shadcn/ui, PostgreSQL, Drizzle, Better Auth (вход по ссылке), Nodemailer (письма), pnpm.
