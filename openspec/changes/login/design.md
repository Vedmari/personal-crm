# Design

## Context

Зачем — см. `proposal.md`, что должно работать — `specs/`.

Сейчас:

- Входа нет. Все запросы в `src/db/queries.ts` читают и меняют все строки, действия в `src/app/actions.ts` принимают номер записи и сразу идут в базу.
- Таблицы `contacts`, `notes`, `groups`, `contact_groups`, номера записей — `integer identity`. Название группы уникально на всю базу (`groups_name_unique_idx`).
- `cacheComponents: true`: чтение `headers()`/`cookies()` возможно только внутри `<Suspense>`. Страницы уже читают данные в компонентах внутри `<Suspense>`.
- Next.js 16: `proxy.ts` вместо middleware, по умолчанию работает в Node.js.
- Выкатка: бэкап → разовый контейнер миграций `scripts/migrate.mts` → новый образ → smoke `/health`. Приложению и миграциям в `deploy/compose.yaml` сейчас передаётся только `DATABASE_URL`.
- Репозиторий публичный: личные адреса и ключи в git попадать не должны.
- Better Auth 1.7.18 и Nodemailer 10.3.1 — последние стабильные версии на 06.11.2026. Факты ниже проверены по документации и исходникам этих версий.

## Goals / Non-Goals

**Goals:**

- Каждый запрос к данным ограничен владельцем на уровне запроса к базе, а не интерфейса.
- Одна сборка: куда уходят письма, адрес приложения и секреты задаются только настройками.
- Существующие данные переходят к владельцу одной миграцией, без потерь. Если что-то не так, выкатка останавливается до старта новой версии.

**Non-Goals:**

- Общий доступ, роли, удаление аккаунта, смена почты (см. `specs/02-пользователи-вход.md`, «Не делать»).
- Кэширование данных между запросами (`use cache`): данные и так читаются на каждый запрос.
- Промежуточная страница «Нажмите, чтобы войти» против почтовых сканеров (см. Risks).

## Decisions

### 1. Better Auth с Drizzle, номера пользователей — текст

`betterAuth({ database: drizzleAdapter(db, { provider: "pg", schema }), plugins: [magicLink(...), nextCookies()] })` в `src/lib/auth.ts`, обработчик — `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler`). `nextCookies()` — последним плагином: он даёт серверным действиям ставить и стирать cookie входа.

Таблицы Better Auth (`user`, `session`, `account`, `verification`) описываю в `src/db/schema.ts` вручную, по составу полей Better Auth 1.7: ключи полей в camelCase, столбцы в snake_case, как у остальных таблиц. `account` вход по ссылке не использует, но таблица нужна: Better Auth сверяет схему при старте.

- Номер пользователя — текст, как по умолчанию в Better Auth. Альтернатива `generateId: "serial"` отвергнута: Better Auth предупреждает, что тогда не работает защита от повторного использования при входе по ссылке.
- CLI `npx auth generate` не берём: это ещё один пакет ради одного запуска, а схема короткая.

### 2. Владелец — столбец `owner_id` у контактов и групп

- `contacts.owner_id` и `groups.owner_id` — `text not null references "user"(id) on delete restrict` (удаления аккаунта нет, случайное удаление пользователя не должно стирать данные). Индексы — по `owner_id`.
- У заметок и `contact_groups` своего владельца нет: заметка принадлежит владельцу контакта (так в спеке), связь «контакт–группа» проверяется по обоим концам.
- Уникальность названия группы — `(owner_id, replace(lower(name), 'ё', 'е'))` вместо уникальности на всю базу.

Альтернатива — `owner_id` и у заметок — отвергнута: два источника правды о владельце, которые могут разойтись.

### 3. Каждый запрос получает владельца первым аргументом

Все функции `src/db/queries.ts` принимают `ownerId: string` первым аргументом, и каждое `where` содержит владельца. Заметки проверяются через `exists (select 1 from contacts where id = notes.contact_id and owner_id = …)`. `setContactGroup` и `createGroupForContact` проверяют, что и контакт, и группа принадлежат владельцу. Чужая запись даёт тот же результат, что несуществующая (`undefined` / `"not_found"`), поэтому действия отвечают прежними текстами «Контакт не найден. Обновите страницу.» и т. п.

`eraseExpiredDeletions` тоже ограничен владельцем: запрос пользователя не трогает чужие строки, даже удалённые.

Альтернатива — запросы сами читают текущего пользователя — отвергнута: владельца легко забыть в новом запросе, а явный аргумент забыть не даст TypeScript. К тому же запросы проще тестировать без подмены сессии.

### 4. Текущий пользователь: `proxy.ts` и проверка на сервере

Проверка в два слоя:

- **`src/proxy.ts`** — на всех путях, кроме `/api/auth/*`, `/health`, `/_next/*` и файлов из `public/`. Вызывает `auth.api.getSession({ headers, returnHeaders: true })`: нет входа — redirect на `/login`; есть вход на `/login` — redirect на `/`. Ответ продления сессии (`Set-Cookie`) копируется в ответ. Это и есть продление «30 дней с последнего захода»: в Server Component Next.js cookie поставить нельзя, а Better Auth там продление пропускает.
- **`src/lib/current-user.ts`** — `getCurrentUser()` в `React.cache` вокруг `auth.api.getSession({ headers: await headers() })` и `requireUserId()`, который без входа делает `redirect("/login")`. Его вызывает каждый компонент страницы, который читает данные (они уже внутри `<Suspense>`), и **каждое** серверное действие до любого обращения к базе. Server Actions — это POST на путь страницы, и документация Next.js прямо требует проверять вход в самом действии, а не полагаться на proxy.

Альтернатива — в proxy только проверять наличие cookie (`getSessionCookie`, без базы) — отвергнута: тогда негде продлевать cookie. Запрос к базе в proxy на каждой странице для личного приложения недорог.

Сессия: `expiresIn` 30 дней, `updateAge` 1 день. Значит, вход заканчивается через 29–30 дней после последнего захода: в пределах дня срок не продлевается, чтобы не писать в базу на каждой странице. Каждый вход по ссылке — отдельная сессия (несколько устройств), «Выйти» (`auth.api.signOut`) удаляет только текущую.

### 5. Запрос ссылки: одна проверка для формы и для прямых запросов

Вся проверка запроса ссылки — в `hooks.before` Better Auth для пути `/sign-in/magic-link`. Хуки срабатывают и на HTTP-запрос к `/api/auth/sign-in/magic-link`, и на вызов `auth.api.signInMagicLink` из серверного действия, поэтому запрос не из формы проходит те же проверки:

1. Почта: `trim().toLowerCase()`, затем та же проверка формата, что у почты контакта. Неверно — `APIError("BAD_REQUEST", { code: "INVALID_EMAIL" })`. Нормализованная почта подменяет `ctx.body.email` (иначе Better Auth отклонит пробелы сам и сохранит почту как набрана).
2. Лимит — см. решение 6.

Форма входа вызывает серверное действие `requestLoginLinkAction`. Оно разбирает почту той же функцией `parseLoginEmail` из `src/lib/validation.ts`, вызывает `auth.api.signInMagicLink({ body: { email, callbackURL: "/", errorCallbackURL: "/login/expired" }, headers })` и переводит коды ошибок в тексты интерфейса: «Проверьте адрес почты» под полем, «Слишком часто, попробуйте через несколько минут», «Не получилось отправить письмо. Попробуйте ещё раз через минуту.». При успехе — «Ссылка для входа отправлена на <нормализованная почта>», форма остаётся на месте (можно исправить опечатку).

Ответ одинаков для новой и известной почты: Better Auth создаёт пользователя только при переходе по ссылке, а запрос ссылки от наличия пользователя не зависит.

### 6. Лимит писем — своя таблица

Встроенный лимит Better Auth считает запросы по IP и пути, а не по почте, и не действует на вызовы `auth.api`. Поэтому своя таблица `login_link_sends (id, email, created_at)` с индексом `(email, created_at)`:

- В хуке, в одной транзакции под `pg_advisory_xact_lock(hashtext(email))`: удалить записи старше 10 минут, посчитать оставшиеся для этой почты, при 3 и больше — `APIError("TOO_MANY_REQUESTS", { code: "TOO_MANY_LINKS" })`, иначе вставить запись. Блокировка не даёт двум одновременным запросам отправить четвёртое письмо.
- Если письмо не ушло, `sendMagicLink` удаляет эту запись: лимит считает отправленные письма, а не попытки.

Встроенный лимит Better Auth по IP оставляем включённым как защиту от рассылки на много разных адресов (в production по умолчанию 5 запросов ссылки в минуту с одного IP). IP он берёт из `x-forwarded-for`, поэтому nginx нашего сайта должен передавать `X-Forwarded-For $remote_addr` (перезаписью, а не дописыванием — иначе адрес подделывается). Для e2e он выключается настройкой `AUTH_IP_RATE_LIMIT=off`: все тесты идут с одного адреса, а `pnpm start` работает в production-режиме.

### 7. Ссылка: 15 минут, один раз, новая отменяет старые

- `magicLink({ expiresIn: 15 * 60, sendMagicLink })`. Better Auth сам делает ссылку одноразовой: строка `verification` удаляется при входе.
- Отмена старых ссылок: в `sendMagicLink` — `delete from verification where identifier like 'magic-link:%' and value::jsonb->>'email' = $email and identifier <> 'magic-link:' || $token`. Better Auth хранит ключ открытым текстом (`storeToken: "plain"`, по умолчанию) в `identifier = magic-link:<ключ>` и почту в JSON `value` — проверено по исходникам 1.7.18. Тест «Запросила ссылку дважды» поймает, если формат изменится в следующей версии.
- Любая ошибка проверки ссылки (Better Auth отдаёт `INVALID_TOKEN` и для старой, и для использованной, и для подделанной) ведёт на `/login/expired`: «Ссылка устарела, запросите новую» и кнопка «Запросить новую ссылку» на `/login`. Редкие ошибки (`failed_to_create_session` при упавшей базе) ведут туда же: запросить новую ссылку — правильный совет и для них.
- После входа всегда открывается `/`: письмо часто открывают на другом устройстве, возвращать на прежнюю страницу некуда.

### 8. Письма: Nodemailer, адрес из `SMTP_URL`

- Один транспорт Nodemailer из строки подключения `SMTP_URL`: на этом компьютере и в CI `smtp://localhost:1025` (Mailpit), на сервере `smtps://resend:<API-ключ>@smtp.resend.com:465`. Код один, отличается только настройка. Транспорт создаётся при первой отправке, а не при импорте: сборке образа `SMTP_URL` не нужен.
- Отправитель — константа в коде `"Личная CRM" <noreply@mail.crm.lichnaya-crm.ru>` (так в спеке, одинаково везде).
- Письмо собирает чистая функция `buildLoginEmail(url)` → `{ subject, html, text }`: HTML-кнопка «Войти» (ссылка, оформленная кнопкой; без картинок и внешних стилей) и текстовая версия со ссылкой. Её проверяет юнит-тест, а доставку — e2e через Mailpit.
- В журнал при сбое отправки — только код ошибки Nodemailer, без адреса: как с запросами к базе (решение от 27 октября 2026).
- Mailpit `axllent/mailpit:v1.33.0` — в `docker-compose.yml` (порты 1025 и 8025 только на `127.0.0.1`) и сервисом в job `E2E` в CI.

### 9. Почта владельца — `OWNER_EMAIL`, данные переходят в миграции

Почта владельца задаётся строкой `OWNER_EMAIL` в `.env` (решение пользователя: в публичном репозитории почты быть не должно).

- `scripts/migrate.mts` приводит `OWNER_EMAIL` к одному виду (та же `normalizeEmail`, что у входа) и на своём единственном подключении вызывает `select set_config('crm.owner_email', $1, false)` до применения миграций. `pnpm db:migrate` переключается с `drizzle-kit migrate` на этот же скрипт (`node --env-file=.env scripts/migrate.mts`): иначе на этом компьютере миграция не узнает почту.
- Миграция `0005` (сгенерирована `drizzle-kit generate` и дописана руками):
  1. создаёт таблицы Better Auth и `login_link_sends`;
  2. добавляет `owner_id` без `not null`;
  3. если в `contacts` или `groups` есть строки — создаёт пользователя с почтой из `current_setting('crm.owner_email', true)` (`id = gen_random_uuid()::text`, `name = ''`, `email_verified = true`), если его ещё нет, и проставляет его `owner_id` всем строкам;
  4. ставит `not null`. Если строки есть, а почта не задана, этот шаг падает. Drizzle применяет все миграции в одной транзакции, поэтому база остаётся как была, а выкатка останавливается до старта нового образа;
  5. меняет уникальный индекс групп.
- Миграция ничего не удаляет. `migrate.mts` печатает число контактов, заметок и групп до и после — в журнале выкатки видно, что записей столько же. Без имён и почты.
- На пустой базе (тесты, CI) почта не нужна: строк нет, `not null` ставится сразу.

Альтернативы: почта в SQL миграции — отвергнута, она попала бы в публичный git; отдельный скрипт «раздать данные» после миграций — отвергнут, потому что тогда `not null` нельзя поставить в той же выкатке, и записи без владельца были бы ни у кого не видны.

`scripts/seed.mts` требует `OWNER_EMAIL`, находит или создаёт этого пользователя и создаёт демо-данные у него. Правило «только на пустой базе» не меняется. `deploy/seed.sh` работает через контейнер `migrate`, которому `OWNER_EMAIL` передаётся.

### 10. Настройки

| Строка | Этот компьютер | CI | Сервер |
| --- | --- | --- | --- |
| `BETTER_AUTH_SECRET` | случайная строка ≥ 32 символов | тестовое значение в workflow | случайная строка, `openssl rand -base64 32` |
| `BETTER_AUTH_URL` | `http://localhost:3000` | `http://localhost:3200` (задаёт `playwright.config.ts`) | `https://app.lichnaya-crm.ru` |
| `SMTP_URL` | `smtp://localhost:1025` | `smtp://localhost:1025` | `smtps://resend:<ключ>@smtp.resend.com:465` |
| `OWNER_EMAIL` | моя почта | не нужна (пустые базы) | моя почта |
| `AUTH_IP_RATE_LIMIT` | — | `off` в job `E2E` | — |

- `BETTER_AUTH_URL` обязателен: без него за nginx ссылки в письмах получили бы внутренний адрес `http://127.0.0.1:3000`.
- `deploy/compose.yaml`: приложению — `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_URL`, контейнеру `migrate` — `OWNER_EMAIL`. Все — через `${…:?Set … in /opt/crm/prod/.env}`: забытая строка останавливает выкатку на первой проверке `compose config`, до бэкапа и миграций.
- `Dockerfile`: на шаге сборки — подставной `BETTER_AUTH_SECRET`, как уже сделано с `DATABASE_URL` (Better Auth начинает проверку настроек при импорте, а `next build` работает в production-режиме). В готовый образ он не попадает.
- `.env.example` — новые строки без значений.

### 11. Интерфейс

- `/login` — лист ежедневника, как другие страницы: логотип, заголовок «Вход», поле «Почта», кнопка «Получить ссылку», под ней сообщения. `/login/expired` — такой же лист с «Ссылка устарела, запросите новую» и кнопкой. Обложка открывается и над страницей входа по своим правилам (первое открытие за сеанс, переход с лендинга).
- Строка над листом: `AccountBar` в `layout.tsx`, в `<Suspense>`, рядом с `{children}`. На сукне, мелким светлым шрифтом через существующие токены: «почта · Выйти». Без входа (страницы входа) ничего не рисует. «Выйти» — форма с серверным действием `signOutAction`: `auth.api.signOut` и redirect на `/login`.
- `src/app/contacts/[id]/not-found.tsx` — тот же вырванный лист, что у общей «Такой страницы нет», но «Контакт не найден». Его получают и несуществующий, и чужой контакт.
- Закладка: в `localStorage` хранится вместе с номером пользователя, чья она. Закладку другого пользователя ribbon не показывает и не называет; «Выйти» её стирает. Номер пользователя закладке передаёт `AccountBar`.

### 12. Тесты

- **Vitest, юнит:** `parseLoginEmail`/`normalizeEmail`, `buildLoginEmail`, разбор чужой закладки.
- **Vitest, база:** `test/setup-db.ts` подменяет модуль `@/lib/current-user` (как уже подменяется `next/cache`): `signInAs(userId)` выбирает, от чьего имени работают действия. Фабрики получают владельца, перед каждым тестом создаются пользователи A и B. Тесты на A/B для каждого запроса и действия (сценарии `data-ownership`), на лимит и отмену старых ссылок (функции хука на настоящей базе), на «Письмо не ушло» (`SMTP_URL` на закрытый порт — настоящий сбой, не подмена). Миграцию `0005` проверяет отдельный тест на временной базе `<рабочая>_migration_test`: миграции до `0004`, данные, затем `0005` с почтой владельца и без неё.
- **Playwright:** проект `setup` (`e2e/auth.setup.ts`) входит под пользователем e2e через форму и Mailpit и сохраняет `storageState` в `e2e/.auth/` (в `.gitignore`); существующие спеки, в том числе главный сценарий, зависят от него — «перед сценарием автотест входит под пользователем». `resetDatabase` чистит только таблицы данных и `login_link_sends`, пользователей и сессии не трогает, исходные контакты кладёт пользователю e2e. Отдельный проект `login` — без сохранённого входа, у каждого теста свои почты, чтобы не мешал лимит: `e2e/login.spec.ts` (сценарии `user-auth` и страницы «Контакт не найден») и `e2e/two-users.spec.ts` — критерий успеха: A и B в двух контекстах браузера, каждый входит по своей ссылке из Mailpit и не видит контактов, заметок и групп другого, в обе стороны. Он отдельный от главного сценария, как требует `specs/02-пользователи-вход.md`. Ссылку берёт `e2e/mailpit.ts` из API Mailpit (`MAILPIT_URL`, по умолчанию `http://localhost:8025`). «Прошло 15 минут», «30 дней», «через 10 минут» — сдвигом времени в строках базы, без ожидания.
- Сценарий `user-auth` «На сервере» (настоящее письмо через Resend) автотеста не имеет: это проверка настоящей выкаткой (CLAUDE.md).

## Risks / Trade-offs

- [Домен отправителя не подтверждён в Resend к моменту выкатки → письма не уходят, войти не может никто, в том числе владелец] → До merge: аккаунт Resend, домен `mail.crm.lichnaya-crm.ru`, записи DNS (делает пользователь), проверка статуса «Verified». После выкатки — вход на сервере руками. Если не работает — откат «база + версия».
- [Почтовые сканеры (защита ссылок в корпоративной почте) открывают ссылку раньше человека → одноразовая ссылка сгорает, человек видит «Ссылка устарела»] → Сейчас ссылка ведёт прямо на вход, как в спеке. Если так случится, предложу промежуточную страницу с кнопкой «Войти» — это изменение поведения, решать пользователю.
- [Better Auth поменяет формат `verification` → отмена старых ссылок тихо перестанет работать] → Версия зафиксирована в `pnpm-lock.yaml`; e2e «Запросила ссылку дважды» упадёт при обновлении.
- [Запрос к базе в `proxy.ts` на каждой странице] → Для одного-двух десятков пользователей незаметно. Статика и `/api/auth` из proxy исключены.
- [Вход держится 29–30, а не ровно 30 дней после последнего захода (`updateAge` 1 день)] → Записано в решения агента в `specs/01`.
- [nginx передаёт `X-Forwarded-For` не так → встроенный лимит по IP общий на всех] → Проверить настройку сайта при выкатке. Общий лимит 5 ссылок в минуту на всех — неудобство, а не дыра: лимит по почте из спеки работает независимо.
- [Старая версия приложения не работает с новой базой: добавление контакта упадёт на `owner_id not null`] → Откат только парой «база из бэкапа перед выкаткой + прошлая версия» (так в спеке), README описывает порядок.
