# Design

## Context

Мотивация — в `proposal.md`, требования — в `specs/contact-list/spec.md`.

Что есть сейчас:

- Главная — серверная страница Next 16 с `cacheComponents`. Поиск (`?q=`) и группа (`?group=`) живут в адресе. Все ссылки на список собирает `listHref`, разбирает адрес `parseListParams` (`src/lib/list-filter.ts`).
- `listContacts(search, groupId)` (`src/db/queries.ts`) отдаёт все подходящие строки и `total` — число контактов в книге или в группе без учёта поиска. Порядок — `name collate "ru-x-icu"`, затем `id`.
- `ContactList` группирует строки по первой букве и рисует счётчик. «Найдено X из Y» берёт X из длины выдачи.
- `revealContact(id)` (`src/lib/reveal-contact.ts`) до 5 секунд ищет строку `contact-<id>`, прокручивает к ней и подсвечивает. Её вызывают после добавления (`AddContactButton`, перед этим `router.replace("/")`, если в адресе что-то было) и после «Вернуть» (`DeleteContactButton`: удаление в карточке ведёт на `/`).
- Строки списка — `content-visibility: auto`: невидимые строки не раскладываются, поэтому `revealContact` после плавной прокрутки доводит её рывком.
- Блок «Пора связаться» и фильтр групп — отдельные запросы, от длины списка не зависят.

## Goals / Non-Goals

**Goals:**

- Первая загрузка главной тянет из базы и отдаёт в браузер не больше 100 строк списка.
- Порции не теряют и не повторяют людей, даже если между нажатиями кто-то добавлен или удалён в другой вкладке.
- Всё поведение со стыками порций, адресом и догрузкой покрыто тестами по TDD: логика адреса — unit, запросы — db-тесты на тестовой базе, путь пользователя — e2e.

**Non-Goals:**

- Ускорение блока «Пора связаться», фильтра групп и карточки.
- Виртуальный список (рисовать только видимые строки): при 100–300 строках его выгода меньше сложности.

## Decisions

### 1. В адресе — сколько показано, а не номер страницы

Параметр `?shown=200`. Сервер каждый раз отдаёт первые `shown` строк выдачи (`limit`, без `offset`) и рисует их одним списком.

- Стык порций не виден: буквы считаются по всему показанному списку, «В» на стыке одна.
- Добавили или удалили кого-то в другой вкладке — список просто пересчитан, людей не теряем и не дублируем.
- Обновление страницы и ссылка дают тот же список без клиентского состояния.

Разбор `shown`: целое число, округляется вверх до кратного 100, меньше 100 или не число — 100. Верхней границы нет: `limit` больше числа строк безвреден. `listHref` пишет `shown` только если он больше 100, поэтому обычный адрес остаётся `/`.

Смена поиска или группы сбрасывает `shown`: `SearchBox` и кнопки групп собирают адрес через `listHref` без `shown`. Это и есть «новый запрос начинает сначала».

Другие варианты:

- `offset` + дописывать порцию на клиенте — меньше трафика на «Показать ещё», но список живёт в клиентском состоянии: обновление и «Назад» его теряют, а сдвиги из других вкладок дают дубли и пропуски.
- Курсор по имени (`name > последнее`) — устойчив к сдвигам, но та же проблема с клиентским состоянием, и курсор по ICU-сортировке с повторяющимися именами сложнее.

Цена решения: каждое «Показать ещё» отдаёт весь список заново. После девятого нажатия на 1000 контактах страница снова весит, как сейчас. Это осознанно: обычно нужного человека ищут поиском, а первая загрузка — самая частая — лёгкая.

### 2. Кнопка «Показать ещё» — ссылка с `replace`

Кнопка — `Link` на `listHref({ q, group, shown: shown + 100 })` с `replace` и `scroll={false}`. Без JavaScript она тоже работает. `replace` не добавляет шаг в историю, `scroll={false}` оставляет страницу на месте. Пока грузится, кнопка показывает «Загружаю…» и не нажимается повторно.

Фокус: после загрузки фокус переходит на ссылку первой новой строки. Номер этой строки (старый `shown`) кнопка знает. Без переноса фокуса пользователь клавиатуры оказался бы на кнопке, которая уехала вниз, или на `body`.

### 3. Запрос отдаёт три числа

`listContacts(search, groupId, limit)` возвращает `items` (не больше `limit`), `matched` (сколько найдено всего, с поиском) и `total` (как сейчас — книга или группа без поиска). Счётчик «Найдено X из Y» берёт X из `matched`, кнопка — остаток `matched - items.length`. Без поиска `matched` равно `total`.

`count` по тем же условиям — отдельный запрос рядом с выборкой, в `Promise.all`. При тысячах строк это миллисекунды, индекс для этого не нужен.

### 4. Место контакта для догрузки

Новый запрос `contactPosition(id)` — номер контакта в полном алфавитном списке без поиска и группы: `count` неудалённых контактов, которые стоят раньше (`(name collate "ru-x-icu", id) < (…)`), плюс один. `createContactAction` и `restoreContactAction` возвращают его в `data.position`.

Клиент считает `shown = ceil(position / 100) * 100`. Если он больше 100 — `router.replace(listHref({ shown }), { scroll: false })`. Затем, как сейчас, `revealContact(id)`: она ждёт строку до 5 секунд.

Почему без поиска и группы: добавление уже сбрасывает их (`router.replace("/")`), а «Вернуть» всегда приходит на `/` из карточки.

Другие варианты:

- `?reveal=<id>` в адресе, сервер сам считает длину — параметр остаётся в адресе и попадает в историю и ссылки.
- Догружать по одной порции, пока строка не появится, — до 10 запросов подряд.

### 5. «Назад» из карточки

App Router при «Назад» берёт страницу `/?shown=200` из клиентского кэша и восстанавливает прокрутку. Это проверяет e2e-сценарий «Назад из карточки». Если восстановление окажется неточным из-за `content-visibility`, запасной путь — запоминать id открытого контакта в `sessionStorage` и после «Назад» вызывать для него `revealContact` без подсветки. Делаем запасной путь, только если тест покажет, что без него контакт не виден.

### 6. Тесты

- Unit (`src/lib/list-filter.test.ts`): разбор `shown`, `listHref` с `shown` и без, сброс `shown` при смене поиска или группы, расчёт `shown` по месту контакта.
- DB (`src/db/list-pages.db.test.ts`): `limit`, `matched` и `total` с поиском и группой, порядок на стыке, `contactPosition` с удалёнными и одинаковыми именами. Действия (`src/app/contact-position-actions.db.test.ts`): `position` у добавления и «Вернуть».
- E2E (`e2e/pagination.spec.ts`): книга из 250 тестовых контактов через `resetDatabase(fill)`. Имена генерирует тест так, чтобы место по алфавиту было предсказуемым. Сценарии со стыком букв, фокусом, «Назад», историей и догрузкой — здесь: их видно только в браузере.

## Risks / Trade-offs

- [Повторная выдача всего списка на каждое «Показать ещё»] → решение 1. Если станет медленно — перейти на `offset` с дописыванием, адрес и требования не меняются.
- [Прокрутка после «Назад» неточна] → e2e-сценарий и запасной путь из решения 5.
- [Фокус после загрузки уходит до того, как строка появилась] → переносим фокус в эффекте после того, как строка с нужным номером есть в DOM; это проверяет e2e.
- [Пограничный `shown` в адресе, например `shown=1e9`] → безвреден: `limit` отдаёт не больше, чем есть. Отрицательное и дробное — 100 и округление вверх.

## Migration Plan

Миграций нет. Выкатка обычная: PR → зелёный CI → автовлитие → Deploy. Откат — revert PR: старые адреса с `?shown=` просто покажут весь список, как раньше.
